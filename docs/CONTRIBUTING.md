# Contributing Guide

This document describes how the team works with Git and GitHub on this
repository.

## Branching

`main` is always kept in a working state. Nobody commits to `main`
directly — every change starts on its own branch.

Branch names follow `<type>/<issue-number>-<short-description>`, where
`<type>` matches the commit type it will contain:

- `feat/41-remove-registered-campsites`
- `fix/52-notification-crash`
- `docs/64-accessibility-guide`

A branch should cover exactly the scope of the issue it's named after.
If a change grows beyond that issue's scope, split the extra work onto
its own branch and issue instead of folding it in.

## Commits

Commits follow the conventional commit format: a single line,
`<type>: <description>`, written in the present tense
(`feat: add campsite search filter`, not `added campsite search
filter`).

Common types used in this repo:

- `feat` — a new feature or behavior
- `fix` — a bug fix
- `docs` — documentation only
- `chore` — build config, dependencies, tooling
- `test` — adding or updating tests
- `refactor` — restructuring code with no behavior change

Each commit should be one logical change. A branch that touches config,
a data model, and a UI screen is three commits, not one, even if they
land in the same PR. Don't amend a commit to absorb unrelated changes —
make a new one.

## Issues and pull requests

Open an issue before starting any non-trivial work, scoped to a single
user story or task. A pull request is opened only once there's a
corresponding issue to tie it to — the exception is something truly
trivial, like fixing a typo.

Keep a PR scoped to what its issue describes. A PR that also includes
an unrelated dependency bump or an unrelated fix should be split into
two PRs instead.

## Opening and reviewing a PR

1. Push the branch and open a PR against `main`.
2. In the PR description, include `Closes #<issue-number>` — this
   links the PR to its issue and automatically closes the issue and
   moves its project board card once the PR merges.
3. Request a review from another team member. **The PR author cannot
   approve or merge their own PR** — at least one other person has to
   review it first.
4. Merge only after it has an approval and any CI checks are passing.

If an issue isn't linked through `Closes #N` for some reason, move its
project board card manually when work starts on it and again once it's
merged.

## Local environment and what not to commit

The repository's root `.gitignore` already excludes files that are
specific to one person's machine or that get regenerated by a build:
`local.properties` (the local Android SDK path), the `build/` and
`.gradle/` output directories, and IDE scratch files under `.idea/`.

Before pushing, check `git status`/`git diff --cached` for anything
that looks machine-specific, regenerable, or like a credential — none
of that should end up in a commit, `.gitignore` or not.
